# implement — 実装

## 前提チェック
- この会話で基本設計が承認されていること。承認済みの設計がこの会話に無い場合（新規タスクとして起動された等）は、設計の内容を貼ってもらうよう依頼して止まる
- 作業ブランチ上であること（main 直接は不可）

## 手順
1. 承認済み設計から実装単位と依存順序を確認し、着手前に単位の一覧を1行ずつ表示する
2. 単位ごとに次を繰り返す
   1. ふるまい仕様からテストを先に書く。公開インタフェース経由で検証し、内部メソッドの呼び出し検証はしない
   2. 実装する。設計のインタフェースを守る
   3. lint とテスト（AGENTS.md のコマンド）を実行し、緑にする
   4. 簡易自己レビュー: 疎結合・高凝集 / ふるまいテスト / 計算量 の3点を確認し、明らかな問題は直す
   5. コミットする: `feat|fix|refactor(<単位名>): <要約>`
   6. 単位の完了を1行で表示する（何を作り、どのテストが通ったか）
3. 依存のない単位は、サブエージェントが使える環境なら並列に割り当てる
   - 各サブエージェントに渡すもの: 担当単位、設計の該当箇所、上記 2-1〜2-5 の手順、コミット規約、下の「書き方」
   - 同じブランチにコミットさせ、他の単位のファイルには触らせない
   - 使えない場合は推奨順序で直列に進める
4. 全単位完了後、全体で lint とテストを実行し、統合で壊れていないか確認する
5. 続けて `code-review` スキルの手順を実行する（同一タスク内で完結させる）

## 書き方（`$sanitize-artifacts` の基準）
- コード、コメント、docstring、テスト名、コミットメッセージに会話の経緯を残さない。「設計どおり」「ユーザーの要望で」「以前は〜だったが」「〜は使わない」は書かない
- コメントは読み手が単体で理解するために必要なことだけ。制約は説明ではなく設計（構造・命名・デフォルト）に溶かす
- コミットメッセージは「何がどう変わるか」を成果物として書く

## 判断が必要になったとき
- 設計の範囲内で吸収できる軽微な判断（命名、内部構造、ログ文言など）: 決めて進め、「決定メモ」として控える。最終報告で一覧にする
- 設計を変える判断（インタフェース変更、ふるまい仕様の追加・変更、スコープ外の修正）: 作業を止め、選択肢と推奨を示して質問する。その時点までのコミットは残す

## 禁止
- 設計に無いふるまいの追加、スコープ外のリファクタ
- テストを弱めて緑にすること（skip、期待値の書き換え、アサーションの削除）
- 単位をまたいだ巨大コミット
