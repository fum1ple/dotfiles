# deliver — 納品

## 手順
1. 状態確認: 作業ブランチの全コミットが lint とテストを通っていること。`git status` で未コミットの変更や一時ファイルが残っていないこと（残っていれば削除するか、意図的なら理由を報告に含める）
2. `$sanitize-artifacts` を差分内の成果物に適用する
   - 対象: 追加・変更したドキュメント、コードコメント、docstring、テスト名、コミットメッセージ（未 push なので必要なら reword）
   - 基準: 会話を見ていない読み手にとって自然に読めるか。「ご要望により」「設計に従い」「以前は」「〜は使わない」「レビュー指摘で」といった経緯・制約・却下案の言及を、説明ではなく設計として溶かすか削除する
   - 修正が出たら lint とテストを再実行し、`docs(<単位名>): <要約>` でコミットする
3. 下のテンプレートで PR タイトルと本文を作る。本文も同じ基準で、PR を単体で読む reviewer 向けに書く
4. PR 作成
   - `gh` が使えるローカル/CLI 環境: `gh pr create` で作成し、URL を報告する
   - cloud タスク: push と PR 作成はできない。本文をそのまま貼れる形で出力し、「Create PR ボタンで作成してください」と伝える
5. 下の報告形式でユーザーに報告する。冒頭に `$show-me` の図を1つ: 変更前後の call tree か file tree の diff（`+`/`-`）で「何が変わったか」を一目で

## PR テンプレート
タイトル: `<種別>: <ふるまいの変化を1行で>`

本文:
```
## 目的
<解決する課題と、変更後のふるまい>

## 変更内容
- <実装単位ごとに1行>

## 設計上の判断
- <実装中に決めたことのうち reviewer が知るべきもの。なければ「なし」>

## テスト
- <追加・変更したふるまいテストの一覧>
- <lint / テストの実行結果>

## 残課題・フォローアップ
- <あれば>
```

## 報告形式（チャット）
1. 変更の全体像（`$show-me` の diff 図1つ＋2〜3行。何ができるようになったかをふるまいで）
2. 決定メモ（設計との差分。なければ「なし」）
3. レビューで報告のみとした P3（あれば）
4. ユーザーに判断してほしいこと（なければ「なし」）
5. PR の URL、または PR タイトルと本文
