# code-review — 4観点レビュー

## 実行モード

依頼に修正の明示がなければ `review-only` とする。

### review-only（既定）
- 差分と周辺コードを読み、指摘と判断根拠を報告する
- ファイル編集とコミットは行わない
- GitHub へのコメント、Approve、Request changes は、明示的に依頼された場合だけ行う
- GitHub へ投稿する直前に最新の head、base、既存 thread、checks、mergeability を取り直し、合意した内容だけを投稿する

### review-and-fix
- 「修正まで」「レビューして直して」など、修正が明示された場合に使う
- P1・P2 を修正し、lint と関連テストを通してコミットする
- 納品や PR 作成は、明示的に依頼された場合だけ行う

## 対象
- ベースブランチからの差分全体: `git diff <base>...HEAD`。base は PR の対象ブランチ、不明なら main
- コミット単位ではなく、揃った状態のコードを見る
- PR レビューでは、最新の PR metadata、base、head、既存コメント、CI を取得する
- 差分を起点に、判断の裏付けに必要な直接の呼び出し元・呼び出し先・テストまで読む

## 判定手順

### Pass 1: 振る舞いと保証を確認する
1. 変更の目的、要件、公開契約を特定する
2. 正常系、失敗、再実行、部分成功で利用者に見える振る舞いを確認する
3. テストがその振る舞いを公開インタフェースの入出力で保証しているか確認する
4. CI、ローカルテスト、マージ可否、実環境での動作を別の証拠として扱う

### Pass 2: 責務と依存を変更単位ごとに確認する
変更・追加されたメソッド（関数を含む）を列挙し、メソッドごとに次の確認表を作業メモへ記録する。クラス・定数だけの変更では、その責務と直接の利用元を対象にする。削除したメソッドは、呼び出し元への影響と責務の移動先を確認する。

| 対象（ファイル・メソッド） | 責務 | 変更理由 | 入出力・依存 | 読んだ根拠 | 判定 |
|---|---|---|---|---|---|
| 対象名 | 仕事を一文で | 何が変わると修正が必要か | 下記の確認結果 | 呼び出し元・生成元・利用先のファイルと行 | 確認済み / 指摘あり / 未確認 |

- 入出力: 異なる意味や処理段階のデータを一つの引数で兼ねていないか。値の有無や呼び出し順で契約が変わらないか。
- 依存: 追加・変更された知識と状態の所有者を特定する。他の処理の内部形式を解釈したり、データを取り出して計算し書き戻したりしていないか。
- 変更理由: 値、表示、業務条件、外部 I/O のどれかを変えた場合に、どの対象へ変更が波及するかを具体的に確認する。
- 根拠: 差分に加え、変更した契約の呼び出し元、値を生成する側、値を利用する側を読む。成功・失敗・拒否などで値の意味が変わる場合は、その生成経路まで追う。テストダブルだけを根拠に実装の契約を判断しない。

各行の判定には短い理由を付ける。参照先を読めない、呼び出し元を特定できないなど、裏付けが不足する場合は `未確認` として対象と理由を残す。問題のないメソッドも省略せず、無関係なコードまで探索を広げない。この表はレビュー用の作業メモとし、リポジトリへの保存は依頼された場合だけ行う。

### 残りの観点を確認する
Pass 1・2 の後に、計算量と過剰さを確認する。振る舞いに問題がないことを、設計にも問題がない根拠として扱わない。

### 指摘候補を絞る
次の条件をすべて満たすものだけを指摘する。

1. 今回の差分が問題を追加・強化したか、変更したコードがその問題へ直接依存している
2. 不具合、変更コスト、性能、または不要な複雑さへの具体的な影響を説明できる
3. 修正する場所と、移動・削除・置換する先を名指しできる
4. 設計指摘では、具体的な変更場面と影響箇所、修正後にその変更を受け持つ場所を説明できる

差分外の既存問題、将来の仮定だけで生じる問題、命名やスタイルの好みは P1・P2 にしない。メソッドの長さ、条件分岐、具象依存という見た目だけで指摘せず、指摘件数を目標にしない。

### レビュー完了条件
総評を書く前に、Pass 2 の対象一覧と確認表を照合し、記録漏れがないことを確認する。各項目を `確認済み / 指摘あり / 未確認` のいずれかに分類する。

- 振る舞いと公開契約
- クラス・メソッド・定数の責務と依存
- テストが保証するふるまい
- 計算量
- 過剰さ

- 「妥当」「問題なし」とするメソッドにも、責務・変更理由・依存関係の根拠があること。テスト成功、既存処理の再利用、レイヤー規則への適合だけで代用しない。
- 未確認事項が残る場合は、確認できた範囲の結果と、未確認の対象・理由を報告する。レビュー全体を完了・問題なしと断定しない。
- 修正後は、影響したメソッドと契約の利用元の記録を更新し、同じ完了条件で判定する。

## 観点と具体的なチェック

### 1. 疎結合・高凝集（クラス・メソッド単位）
- 一つのクラス・メソッドが複数の理由で変更されないか
- データ、表示、業務判断、外部 I/O の知識が、その責務を持つ対象に置かれているか
- 呼び出し元が他クラスからデータを取り出し、計算して書き戻していないか
- 依存がレイヤーやモジュールの境界に沿って一方向か
- 他クラスの定数、フィールド、内部コレクションを使って自分の内部状態を組み立てていないか
- 引数や戻り値の変更が、不必要に複数の呼び出し元へ波及しないか
- フラグ引数、呼び出し順、共有された可変状態による暗黙の結合がないか
- 同じ知識が複数箇所に書かれていないか

### 2. ふるまいテストになっているか
- 公開インタフェースの入出力で検証しているか
- 内部メソッドの呼び出し回数・順序、プライベート状態を検証していないか
- モックが外部 I/O に限られているか。自作クラスをモックしていないか
- テスト名が「どの条件で何が起きるか」を説明しているか
- 同じふるまいのまま実装を書き換えたとき、テストが壊れないか
- テスト成功が保証する範囲と、保証しない範囲を区別できるか

### 3. 計算量
- 不要なループのネスト、同じ計算の繰り返し
- N+1（ループ内のクエリ / API 呼び出し）
- コレクションの不要なコピー、全件読み込み、線形探索の繰り返し（set/dict で置けるもの）
- 大きなデータのメモリ保持

### 4. 過剰さ
削れるものを4種類で見る。

**使われていない**（消すだけでよい）
- 呼び出し元のない関数・エクスポート、渡されるが読まれない引数、到達しない分岐
- 起きない例外の catch、冪等な処理を包むリトライ、上流で保証済みの再検証
- 設定されないフラグ・環境変数・オプション

**既にある**（自分で書かなくてよい）
- 既存のヘルパー・ユーティリティ・パターンの再実装
- 標準ライブラリやプラットフォーム機能で足りるものの手書き
- 新しい依存の追加。導入済みの依存で足りないか

**まだ要らない**（今は1つで足りる）
- 実装が1つしかない抽象、呼び出し元が1つの層、誰も設定しない設定
- 使われていない汎用引数・拡張点

**二重に持っている**（1つでよい）
- 計算で出せる値の保存、更新元が2つある状態
- 詰め替えだけの中間表現

同じ結果をより短く書けるなら、その形を示す。

指摘は「場所 / 何を消すか / 何に置き換えるか」で書く。置き換え先を名指しできないものは出さない。使われていないものを消す指摘は、置き換え先が「なし」でよい。

観点1との境界は、ロジックの重複なら1、保存された値の重複なら4。同じ計算式が2箇所にあるなら1、計算結果をカラムに持っているなら4。
観点3との境界は、性能の話なら3、存在理由の話なら4。全件読み込みが遅いなら3、その集計自体が要らないなら4。

削らないもの: 信頼境界の入力検証、データ損失を防ぐエラー処理、セキュリティ、アクセシビリティ、明示的に依頼されたもの。非自明なロジックの検証は1つ残す。行数の削減自体を目的にしない。

## 重要度
- P1: 観点に明確に反しており、放置すると変更コストや性能に効く → 必ず修正
- P2: 改善した方がよい → 修正する。工数が大きければ報告に回す
- P3: 好み・微細 → 報告のみ

## 結果への反映

### review-only
1. 指摘を `ファイル:行 / 重要度 / 観点 / 問題 / 修正案` の形で整理する
2. 振る舞いと設計を分けて結論を出す
3. P1・P2 は修正案または投稿用コメント案として提示する
4. ユーザーが GitHub 投稿を明示していなければ、チャットで報告して終了する

### review-and-fix
1. 指摘を `ファイル:行 / 重要度 / 観点 / 問題 / 修正案` の形で整理する
2. P1・P2 を修正する。ふるまいを変えず、既存テストを維持する
3. lint と関連テストを実行する
4. 実装単位ごとに `review(<単位名>): <要約>` でコミットする
5. 4観点を再確認し、新たな P1 がないことを確かめる
6. 変更と検証結果を報告して終了する

## 報告
- 指摘は表で示す: 指摘 / 重要度 / 観点 / 対応
- P1 を修正した場合は、問題と修正内容を1〜2行で説明し、必要なら責務や計算の流れが分かる小さな図を添える
- 指摘がない場合も、振る舞いと設計の判断根拠を短く示す。メソッド別の確認済み・指摘あり・未確認の件数を添え、確認表は詳細を求められた場合に提示する
- CI、ローカルテスト、マージ可否、実環境の確認結果を混同しない

## 禁止
- 観点外の指摘で差分を膨らませること
- レビューを口実にしたスコープ外のリファクタ
- `review-only` でファイルを編集・コミットすること
- 明示的な依頼なしに GitHub へ投稿すること
- 未確認事項を問題なしとして扱うこと
