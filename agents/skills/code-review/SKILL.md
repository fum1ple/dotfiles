# code-review — 4観点レビューと反映

## 対象
- ベースブランチからの差分全体: `git diff <base>...HEAD`。base は PR の対象ブランチ、不明なら main
- コミット単位ではなく、揃った状態のコードを見る

## 観点と具体的なチェック

### 1. 疎結合・高凝集（クラス・メソッド単位）
- 1つのクラス/メソッドが複数の理由で変更されないか（責務の混在）
- 他クラスの内部構造（フィールド、内部コレクション）に手を突っ込んでいないか
- 依存が具象ではなく抽象に向いているか。外部 I/O は差し替えられるか
- 引数が多すぎないか。フラグ引数で分岐していないか
- 同じ知識が2か所に書かれていないか

### 2. ふるまいテストになっているか
- 公開インタフェースの入出力で検証しているか
- 内部メソッドの呼び出し回数・順序、プライベート状態を検証していないか
- モックが外部 I/O に限られているか。自作クラスをモックしていないか
- テスト名がふるまいを説明しているか（メソッド名の羅列ではなく「〜のとき〜になる」）
- 同じふるまいのまま実装を書き換えたとき、テストが壊れないか

### 3. 計算量
- 不要なループのネスト、同じ計算の繰り返し
- N+1（ループ内のクエリ / API 呼び出し）
- コレクションの不要なコピー、全件読み込み、線形探索の繰り返し（set/dict で置けるもの）
- 大きなデータのメモリ保持

### 4. 過剰さ
削れるものを4種類で見る。

**使われていない**（消すだけでよい）
- 呼び出し元のない関数・エクスポート、渡されるが読まれない引数、到達しない分岐
- 起きない例外の catch、冪等な処理を包むリトライ、上流で保証済みの再検証
- 設定されないフラグ・環境変数・オプション

**既にある**（自分で書かなくてよい）
- 既存のヘルパー・ユーティリティ・パターンの再実装
- 標準ライブラリやプラットフォーム機能で足りるものの手書き
- 新しい依存の追加。導入済みの依存で足りないか

**まだ要らない**（今は1つで足りる）
- 実装が1つしかない抽象、呼び出し元が1つの層、誰も設定しない設定
- 使われていない汎用引数・拡張点

**二重に持っている**（1つでよい）
- 計算で出せる値の保存、更新元が2つある状態
- 詰め替えだけの中間表現

同じ結果をより短く書けるなら、その形を示す。

指摘は「場所 / 何を消すか / 何に置き換えるか」で書く。置き換え先を名指しできないものは出さない。使われていないものを消す指摘は、置き換え先が「なし」でよい。

観点1との境界は、ロジックの重複なら1、保存された値の重複なら4。同じ計算式が2箇所にあるなら1、計算結果をカラムに持っているなら4。
観点3との境界は、性能の話なら3、存在理由の話なら4。全件読み込みが遅いなら3、その集計自体が要らないなら4。

削らないもの: 信頼境界の入力検証、データ損失を防ぐエラー処理、セキュリティ、アクセシビリティ、明示的に依頼されたもの。非自明なロジックの検証は1つ残す。行数の削減自体を目的にしない。

## 重要度
- P1: 観点に明確に反しており、放置すると変更コストや性能に効く → 必ず修正
- P2: 改善した方がよい → 修正する。工数が大きければ報告に回す
- P3: 好み・微細 → 報告のみ

## 手順
1. 差分を観点ごとに読み、指摘を `ファイル:行 / 重要度 / 観点 / 問題 / 修正案` の形で列挙する
2. P1・P2 を修正する。修正はふるまいを変えないこと（既存テストが緑のまま）。コメントやコミットメッセージは `$sanitize-artifacts` の基準で（「レビュー指摘により」等は書かない）
3. lint とテストを実行し、緑を確認する
4. コミットする: `review(<単位名>): <要約>`。複数の単位にまたがる場合は単位ごとに分ける
5. 修正後に観点1〜4を再度確認し、新たな P1 がないことを確かめる
6. 結果を `$show-me` の流儀で提示する
   - 指摘の一覧: 表（指摘 / 重要度 / 観点 / 対応: 修正済み・報告のみ）
   - P1 の修正: 「なぜ問題で、どう直したか」を1〜2行で噛み砕き、call tree か pseudocode の diff（`+`/`-`）を1つ添える。観点1なら責務の移動が見える call tree の diff、観点2ならテストの検証対象が変わる pseudocode の diff、観点3なら計算の流れの diff、観点4なら削除後の形が見える diff（`-` 中心）
   - cloud では HTML ファイルは開けないので、図はコードブロック内のものに限る
7. レビュー結果を報告して終了する。納品やPR作成は、明示的に依頼された場合だけ行う。

## 禁止
- 観点外の指摘で差分を膨らませること（スタイルや命名の好みは P3 に留める）
- レビューを口実にしたスコープ外のリファクタ
