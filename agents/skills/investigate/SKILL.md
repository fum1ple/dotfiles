# investigate — 調査と対応方針

## ゴール
ユーザーが「どの方針で進めるか」を判断できる材料を揃え、承認を求めて止まる。成果物はファイルではなく、この会話での説明。

## 手順
1. 入力を整理する
   - 要件か課題（バグ）かを判定する
   - バグなら再現条件を特定し、可能なら失敗する再現テストを書いて失敗を確認する（コミットはしない。実装フェーズで扱う）
   - 調査で解消できない不明点は「未確認事項」として説明に含める。推測で進められる範囲は進める
2. リポジトリを調査する
   - 関連するモジュール・クラス・メソッド、既存テスト、類似の実装パターン、呼び出し元と呼び出し先
   - 根本原因を特定する。症状が出る場所ではなく、原因が生まれる場所を突き止める
3. 対応方針を2〜3案作る
   - 粒度は「システムがどのようなふるまいになるか」。実装手段ではなく振る舞いの変化で書く
   - 各案に: 変更後のふるまい / 影響範囲 / リスク / 相対的な工数
   - 推奨案は根本解決とする。最小変更案も併記するが推奨にはしない
4. `$show-me` の流儀で提示する。散文は短く、図はそれを支える文の隣に置く。要点が伝わる最小の図を選び、全部は使わない
   - 現状のふるまい: 関係する処理の call tree、または Mermaid の sequenceDiagram
   - 根本原因: 該当箇所の pseudocode（原因の行に印を付ける）と `ファイル:行`
   - 各案で変わるふるまい: pseudocode か call tree の diff（`+`/`-`）。案ごとに1つ
   - 案の比較: 表（案 / ふるまい / 影響範囲 / リスク / 工数）
   - cloud では HTML ファイルは開けないので、図はコードブロック内のものに限る
5. 説明文は `$sanitize-artifacts` の基準で書く: 「ご依頼の〜」「先ほどの会話で」といった経緯を書かず、判断者が必要な事実と選択肢だけを、一貫した語彙で
6. 承認を求めて終了する

## 終了時の出力（この順で）
1. 課題の要約（3行以内）
2. 現状のふるまいと根本原因（図＋短文）
3. 対応方針の比較（推奨案を先頭に。各案に図1つ＋比較表）
4. 未確認事項（あれば）
5. 質問: 「どの案で進めますか？」

## 禁止
- 設計や実装に進むこと
- 方針を1案だけ提示すること（トレードオフを隠さない）
- 図なしに散文だけで説明すること、逆に図を並べて散文で結ばないこと
