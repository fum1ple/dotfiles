# basic-design — 基本設計

## 前提チェック
- この会話で対応方針が承認されていること。なければ止まって確認する
- 承認された方針の内容を冒頭で1〜2行で再掲し、認識を揃える

## 設計に含めること（この順で）
1. スコープ: 変更するモジュール / 変更しないモジュール
2. 構造: 新規・変更するクラス/モジュールと責務（1つにつき1行）。依存の向き
3. 公開インタフェース: シグネチャ（引数・戻り値・例外）。呼び出し側から見える変化
4. ふるまい仕様: 「前提 / 操作 / 期待結果」の形で列挙。正常系・境界・異常系。これがそのままテストケースになる
5. データとエラー: 状態の持ち方、エラーの伝播、後方互換
6. テスト方針: どの層で何をふるまいテストするか。モックは外部 I/O に限る
7. 実装単位と依存関係: 独立して実装・テスト・コミットできる単位に分割し、依存と推奨順序を示す。並列可能な単位を明示する
8. リスクと未決事項

## 手順
1. 前提チェック
2. 方針に沿って設計する。既存コードの構造に合わせつつ、クラス・メソッド単位で疎結合・高凝集になるように境界を引く
3. `$show-me` の流儀で提示する。要点が伝わる最小の図を選び、散文は図の隣に短く
   - スコープと構造: 責務コメント付きの浅い file tree。変更は `+`/`-` の diff 形式で現状との差を示す
   - 依存の向きと公開インタフェース: call tree（呼ぶ側→呼ばれる側）。新規・変更点は diff 形式
   - ふるまい仕様: 表（前提 / 操作 / 期待結果）。処理の流れが要点なら Mermaid の sequenceDiagram を1つ
   - 実装単位: file tree に単位番号を注記し、依存関係と並列可否を短く
   - 「なぜこの境界か」を疎結合・高凝集の観点から一言ずつ添える
   - cloud では HTML ファイルは開けないので、図はコードブロック内のものに限る
4. 説明文は `$sanitize-artifacts` の基準で書く: 方針の合意経緯や却下した案の話を混ぜず、設計そのものを単体で読める形に
5. 承認を求めて終了する

## 終了時の出力
1. 承認済み方針の再掲（1〜2行）
2. 構造とインタフェース（図＋短文）
3. ふるまい仕様の表
4. 実装単位の一覧と並列可否
5. 未決事項（あれば）
6. 質問: 「この設計で実装に進んでよいですか？」

## 禁止
- プロダクションコードを書くこと
- 方針で合意していないふるまいを追加すること
- ファイルに設計を書いて説明を省くこと
