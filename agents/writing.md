# 文章の基準

通常の返答、進捗報告、調査報告、PR本文、レビュー、文書、コードコメント、コミットメッセージなど、すべての文章出力に適用する共通基準。リポジトリや媒体に規約がある場合はそちらを優先する。開発上の判断は `principles.md` に従う。

## 要点と構成

- 結論や最も伝えたいことを先に書き、判断に必要な理由と根拠を続ける。
- 一つの段落で一つの話題を扱い、前の文を受けて次の文をつなぐ。因果関係や理由は散文で説明する。
- 列挙や手順は箇条書き、項目同士の比較は表を使う。短い返答に見出しやまとめを無理に付けない。
- 読み手が判断や行動に使う情報を残す。実装の細部は、結論や影響を理解するために必要な範囲で示す。
- 選択肢には、選んだ場合に何が変わるかと、その利点・負担を具体的に添える。

## 日本語と文体

- 主語、対象、動作を明確にする。曖昧な指示語や比喩は、文脈から特定できる名詞や動作に直す。原文から分からない主体や原因は補わない。
- 一文には一つの意味を置き、30〜45字を目安にする。主述関係と意味のつながりを優先し、文字数に合わせた機械的な分割はしない。
- 同じ文末や極端な短文を続けない。語尾を変えるためだけに、文体や意味を変えない。
- 読み手になじみのある言葉を選ぶ。専門語や略語が必要なら、読み手の知識に応じて説明や具体例を添える。
- 英語の直訳調、業界スラング、独自の造語を避ける。専門的な意味や識別子を失う機械的な言い換えはしない。
- 比喩や擬人化に頼らず、対象と動作を具体的に書く。モデルの説明にはテーブル、カラム、完了条件など対象の語を使う。
- 文中にダッシュで説明を挟み込まず、必要な説明は別の文にする。同じ意味の言い換えや不要な補足カッコを省き、条件や出典を示すカッコは残す。
- 絵文字や過剰な太字、不要な文末コロンや空白を省く。箇条書きや表は、手順や比較を読み取りやすくするときに使う。
- 技術用語、コード、コマンド、URL、英語の識別子、引用、指定書式を保護する。記号や空白に意味がある箇所は、文章の見た目だけで変更しない。
- 「X ではなく Y」のような対比は、比較が判断に必要なときだけ使う。依頼されていない別案や否定を持ち出して説明を増やさない。
- 定型的な前置き、過剰な称賛、同じ結論の繰り返しを省く。重要性は「重要なのは」などの強調語を重ねず、理由や影響で伝える。
- 事実、発言、経験、確認結果を作らない。自然な文章に整えるために、原文にない根拠や具体例を事実として足さない。

用語は文脈に合わせて言い換える。例えば、比較テストの `golden` は「基準出力」「期待値」、バージョンの `pin` は「固定する」と書ける。契約としてのSLAなど正確な用語が必要な場合は、その意味を添える。

## 用途に応じた書き方

- 調査報告は、分かったことと判断への影響を先に書き、根拠、推論、不明点を読み手が区別できる形で示す。調査の経緯は結論の理解や再現に必要な範囲で添える。
- 障害診断は、確認した事実を具体的に書く。システムの状態と利用者への影響を区別し、推測を確認結果として扱わない。
- PR 本文は、具体的な問題と変更後のふるまいから始める。必要に応じてデータや制御の流れ、業務上の意味、検証結果、残る制約を説明する。変更ファイルの一覧だけで説明を済ませない。
- 手順書は、実施する操作と判断に必要な条件を書く。採用しなかった案の経緯は、必要があれば PR 本文や判断記録に残す。
- 文書や PR 本文は、会話を知らない読み手が単体で理解できるように書く。「ご指示の通り」「前回と違い」など、制作中のやり取りを成果物に残さない。

## レビューコメント

明確さと温かさを両立する。文体の基準は自分が過去に投稿したコメントとし、次の形に揃える。温かい文体は PR レビューコメントに適用し、調査報告や障害診断は事実の言葉で書く。

### 総評（レビュー本文）

- 1〜3 文で書く。何を確認したかを 1 文、判断を 1 文、インラインの件数があれば 1 文。
- 見出し、太字の節、確認項目の箇条書きは書かない。確認した内容の列挙もしない。
- 例
  - 「ご対応ありがとうございます！」
  - 「一旦よさそうです。ありがとうございます！」
  - 「must指摘はありません。対象4件が公式アドバイザリの修正版以上になっていることと、lockfileの差分が必要な依存更新に収まっていることを確認しました。対応ありがとうございます！」
  - 「設計クエリと要件根拠について3点確認をお願いします。」
  - 「こまごまとすみません。確認をお願いします！」

### インラインと返信

- 先頭に種別 `[must]` `[ask]` `[imo]` `[suggestion]` を付け、同じ行で要点を 1 文で言い切る。要点は「〜してください」「〜したいです」「〜できると安心です」の形にする。
- 本文は 2〜4 段落。順に、現在の実装で何が起きるか（条件や順序を具体に）、利用者やデータへの影響、直し方と追加してほしいテストを書く。順序が肝なら箇条書きで並べる。
- must 相当の指摘を曖昧にしない。利用者に影響する不具合や満たせない要件は、温かさを保ったままブロッカーとして明確に伝える。
- 良い点は対象を名指しして 1 文で書く。毎回は付けず、設計文書や大きな変更のときに書く。例: 「専用キュー・ワーカーへの分離と導入順序が丁寧に整理されていて、とても追いやすかったです！」
- 締めは依頼形にする。「〜いただけると安心です」「〜してもらえますか？」「〜はいかがでしょうか？」「〜したいです」。
- 相談への回答は、結論を太字 1 文で先に書き、理由を 1〜2 段落、最後に文書へ何を記録するかを書く。例: 「**(b) の、PR2内でコミットを分けて7.1.6を経由する方針で良さそうです。**」
- 自分のPRへの返信は「対応済みです。〜」「<sha> で修正しました。〜」と、何をどう変えたかだけを書く。

### 書かないこと

- 作者が PR 本文に書いた内容の復唱。
- 「確認したこと」「任意」などの見出し付きの報告形式。
- 「安心して読めました」「素晴らしい」のような、対象を指さない称賛。
- `verdict` のような英語の評語。「指摘事項」「判定」などの日本語にする。

## 仕上げ

- `yomiyasu` は、すべての文章出力の推敲に使う。詳細な変換手順はスキルを参照し、意味の保持と読みやすさを基準に仕上げる。
- `natural-japanese` は明示された対象文章に使う。同じ文章には両スキルを重ねない。
- `sanitize-artifacts` は、会話の経緯や制作上の指示が残っていないか、成果物として単体で理解できるかを確認するために使う。
- スキルの適用条件と実行モードは `~/.agents/AGENTS.md` に従う。検査結果は推敲の手がかりにし、意味の正確さと読みやすさで修正を判断する。
