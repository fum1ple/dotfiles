# AGENTS.md

このファイルは目次です。詳細は各スキル（`$investigate` `$basic-design` `$implement` `$code-review` `$deliver`）を参照すること。

## 作業の進め方
- 要件・課題・バグを受け取ったら、いきなり実装せず `$investigate` から始める
- フェーズ: investigate（調査・対応方針）→ basic-design（基本設計）→ implement（実装）→ code-review（レビュー）→ deliver（納品）
- 対応方針と基本設計は、それぞれユーザーの明示的な承認を得てから次へ進む。承認はこの会話の中で得る（ファイルには書かない）
- 合意ゲートでの説明は `$show-me` の流儀で行う: 散文は短く、要点が伝わる最小の図（call tree / pseudocode / 浅い file tree / diff / Mermaid）を、それを支える短い文の隣に置く。cloud では HTML ファイルは開けないので、図はコードブロック内のものに限る
- 説明・PR 本文・ドキュメント・コードコメント・コミットメッセージは `$sanitize-artifacts` の基準で書く: 会話の経緯（「ご指示の通り」「前回と違い」「〜は使わない方針なので」）を残さず、読み手が単体で理解できる成果物にする
- 修正は最小変更より根本解決を優先する。トレードオフがあるときは両案を提示してユーザーに選んでもらう
- 設計に書かれていない判断が必要になったとき
  - 設計の範囲内で吸収できる軽微な判断（命名、内部構造、ログ文言）: 決めて進め、「決定メモ」として最終報告に含める
  - 設計を変える判断（インタフェース変更、ふるまいの追加・変更、スコープ外の修正）: 止めて質問する

## コミット
- 実装単位ごとにコミットする。メッセージは `<種別>(<単位>): <要約>`。種別は feat / fix / refactor / test / docs / review
- main には直接コミットしない

## Review guidelines
- クラス・メソッド単位で疎結合・高凝集になっているか。1つのクラス/メソッドが複数の理由で変更されないか。依存が抽象に向いているか。引数や戻り値で内部構造を漏らしていないか
- テストが実装詳細ではなくふるまいを検証しているか。公開インタフェース経由で入出力を検証し、内部メソッドの呼び出し回数やプライベート状態を検証していないか。同じふるまいのまま実装を書き換えてもテストが壊れないか
- 不必要に計算量を増やしていないか。ループのネスト、同じ値の再計算、N+1、コレクションの不要なコピー、全件読み込みがないか
- 上記のいずれかに明確に反する場合は P1 として指摘する
